# Discrete tactical interface (action-v4): primitive audit — verdict D

**Question.** Can the existing deterministic guidance primitives support a hierarchical discrete A1 interface {BASE, LEFT, RIGHT, CLIMB}
that is driven by the *defender*, without new maneuver geometry, without touching canonical A0, the V2 environment or the common obstacle layer?

**Pre-registered hypothesis (recorded before implementation).** A hierarchical attacker that selects deterministic tactical maneuver primitives can
provide learned defender-evasion authority while preserving the safety and mission-directed behavior of the canonical obstacle-navigation layer.

**Result.** The hypothesis cannot be tested with the existing primitives. **Verdict D — existing guidance primitives cannot support A1 without new tactical geometry.**
The task instructions require stopping here; no action-v4 interface was implemented, no stress study run, no PPO trained, no protocol tag created.
Machine-readable evidence: `primitive_audit.json` (generated by `experiments/journal_v2_a1_v4_primitive_audit.py`, 9 locking tests).

## 1. Audit of every candidate primitive

| Primitive (file → function) | Inputs | Needs a blocker | Defender-aware | Self-terminating | Repeated call | Clear space |
|---|---|---|---|---|---|---|
| **BASE**: `soldier_env.SoldierEnv._move_enemy` (V2: `u_base = r_hat`) | asset–attacker vector | no | no | n/a | stateless | yes |

No primitive is simultaneously defender-driven and a LEFT/RIGHT/CLIMB maneuver.

## 2. Empirical facts (live code, `primitive_audit.json`)

* **Signatures:** none of `guidance_command`, `lateral_guidance`, `climb_guidance`, `StatefulAvoidanceController.plan`, `ObstacleAvoidancePlanner.plan` or `generate_bypass_candidates` has a defender parameter; `plan` has no mode/action parameter, so a policy cannot *request* a mode.
* **Clear space:** over 2,000 random states, LEFT, RIGHT and CLIMB with no blockers are bit-identical to the mission command in 2,000/2,000 cases. In C0 all four discrete actions would therefore be BASE.
* **CLIMB is finite** (ascends only below `top + clearance`, holds altitude at the cap) and the laws are deterministic pure functions. The finite/non-hovering requirement of the interface would be met — but only where a blocker exists.
* **When are the primitives even defined during the defender-threat window?** Matched canonical-A0 traces (2,000 episodes, 21,169 steps, all five fixed defenders), threat gate = the existing observation gate `enemy_defender_detection_range` = 25 m:

| Level | steps with defender ≤ 25 m | of which avoidance active (blocker set non-empty) | episodes with both |
|---|---:|---:|---:|
| C0 | 2,364 | **0 (0%)** | 0 |
| C1 | 2,376 | **0 (0%)** | 0 |
| C2 | 2,356 | 25 (**1.1%**) | 15 |
| C3 | 2,340 | 60 (**2.6%**) | 40 |

## 3. Why this is decisive

1. In the steps where an attacker has to react to a defender (defender ≤ 25 m), the primitives are undefined in 97–100% of them, so a LEFT/RIGHT/CLIMB request would execute BASE.
2. In the few steps where they are defined, the required authority hierarchy (frozen common obstacle planner above A1) means A1 may not steer, because avoidance owns steering exactly when a blocker set exists.
3. The only way to obtain a defender-driven lateral/vertical maneuver is to define a **reference axis, an offset and a finite duration relative to the defender or the asset** — new tactical geometry, which this task forbids.
4. Using the obstacle routines with an artificial blocker (for example the nearest perceived building, or a virtual obstacle at the defender) would make the maneuver depend on the obstacle layout, not on the threat, and would be an invention presented as reuse.

An interface built on the existing primitives would therefore be **safe by construction and scientifically empty**: a discrete policy whose three non-BASE actions are inert in the circumstances that matter.
(That would be verdict B; verdict D is the stronger and more accurate statement because the problem is the absence of defender-driven geometry, not merely a measured lack of effect.)

## 4. Observation / state note (no change made)
The existing 37-D `a1_v2_obs_v1` exposes the defender block only within the 25 m gate (index 9 detected flag, 10–15 defender state), the 20 obstacle-sector features and the endurance fraction. A maneuver state machine would add hidden state
(active maneuver, time since activation, suppression/rejoin) that is **not** observable; a v4 interface would need at minimum a maneuver phase feature (versioned `a1_v2_obs_v2`). Not implemented, since the architecture itself is not viable.

## 5. What would be needed (not done; each needs its own pre-registration)
A new, explicit, defender-relative maneuver definition — for example a finite **lateral sidestep** (offset ±d perpendicular to the attacker–asset line, with a deterministic return law) and a finite **altitude change** — executed through the frozen common layer so that obstacle avoidance remains authoritative.
Its safety must be demonstrated against the frozen layer with the zero-gained-collision criterion before any learning. This is new geometry and therefore a design decision for the authors, not an application of existing code.
